Project: Nexus CLM
Target Length: 15-20 minutes

Intro

Hi everyone, in this video I will explain the code of my Nexus CLM project.

This is a full-stack Contract Lifecycle Management application. The frontend is built with React and Vite, the backend is built with Node.js and Express, and MongoDB is used as the database.

I will explain the important files only, but I will cover the complete flow: frontend pages, backend APIs, database models, authentication, contract management, and user management.


1. Project Structure

The project has two main folders.

backend contains the Express server, MongoDB models, routes, seed data, and environment configuration.

lexis-react contains the React frontend, components, styling, and API calls.

The main database is MongoDB, and it contains two main collections: users and contracts.


2. Backend Entry Point: server.js

First, I will explain backend/server.js.

This is the main backend file. It imports Express, Mongoose, CORS, dotenv, routes, and the seed function.

Code block:

```js
import express from 'express';
import mongoose from 'mongoose';
import cors from 'cors';
import dotenv from 'dotenv';
import contractRoutes from './routes/contractRoutes.js';
import userRoutes from './routes/userRoutes.js';
import { seedDatabase } from './seedData.js';
```

Express creates the backend server. Mongoose connects to MongoDB. CORS allows the React frontend to call backend APIs. Dotenv loads environment variables from the .env file.

The .env file contains the backend port and MongoDB URL.

Code block:

```js
dotenv.config({ path: path.join(__dirname, '.env') });

const app = express();
const PORT = process.env.PORT || 5000;
```

Then middleware is added.

Code block:

```js
app.use(cors());
app.use(express.json());
```

cors allows frontend-backend communication, and express.json allows the backend to read JSON request bodies.

Then API routes are connected.

Code block:

```js
app.use('/api/contracts', contractRoutes);
app.use('/api/users', userRoutes);
app.use('/uploads', express.static(path.join(__dirname, 'uploads')));
```

So contract APIs start with /api/contracts, user APIs start with /api/users, and uploaded files are served from /uploads.

Finally, the backend connects to MongoDB and starts the server.

Code block:

```js
mongoose.connect(process.env.MONGO_URI)
  .then(async () => {
    console.log('Connected to MongoDB');
    await seedDatabase();
    app.listen(PORT, () => {
      console.log(`Server running on port ${PORT}`);
    });
  })
  .catch((err) => console.log('Error connecting to MongoDB:', err.message));
```

This means when the server starts, it connects to MongoDB, seeds demo data if needed, and then listens on port 5000.


3. User Model: models/User.js

Next is backend/models/User.js.

This file defines the structure of a user document in MongoDB.

Code block:

```js
const UserSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, required: true, unique: true },
  password: { type: String, required: true },
  role: { type: String, enum: ['Admin', 'Manager', 'User'], default: 'User' },
}, { timestamps: true });

export default mongoose.model('User', UserSchema);
```

Each user has a name, email, password, and role.

The role controls access in the frontend. Admin has full access, Manager has dashboard and team access, and User has limited access.

timestamps automatically adds createdAt and updatedAt.


4. Contract Model: models/Contract.js

Next is backend/models/Contract.js.

This file defines the contract document structure.

A contract has multiple nested sections, so the file defines small schemas first: clauses, risks, documents, approval chain, timeline, and stages.

Code block:

```js
const ClauseSchema = new mongoose.Schema({
  num: String,
  name: String,
  status: { type: String, enum: ['Approved', 'Flagged', 'Review', 'Draft'] },
  color: { type: String, enum: ['green', 'red', 'amber', 'gray'] }
});
```

Clauses store individual contract clauses and their status.

Code block:

```js
const RiskSchema = new mongoose.Schema({
  title: String,
  desc: String,
  color: { type: String, enum: ['green', 'red', 'amber'] },
  action: String
});
```

Risks store alerts like missing clauses, overdue approvals, or legal issues.

The main contract schema stores all contract data.

Code block:

```js
const ContractSchema = new mongoose.Schema({
  ref: { type: String, required: true, unique: true },
  name: { type: String, required: true },
  party: { type: String, required: true },
  type: { type: String, required: true },
  value: String,
  stage: { type: String, required: true },
  stageIndex: Number,
  urgency: { type: String, enum: ['red', 'amber', 'green', 'blue', 'gray'] },
  createdBy: { type: mongoose.Schema.Types.ObjectId, ref: 'User' },
  clauses: [ClauseSchema],
  risks: [RiskSchema],
  documents: [DocumentSchema],
  approvalChain: [ApprovalStepSchema],
  timeline: [TimelineEntrySchema],
  stages: [StageSchema]
}, { timestamps: true });
```

The important field here is createdBy, because it connects a contract to the user who created it.

The arrays store the full lifecycle information of the contract.

6. User Routes: routes/userRoutes.js

Next is backend/routes/userRoutes.js.

This file handles user APIs.

First, GET /api/users fetches all users.

Code block:

```js
router.get('/', async (req, res) => {
  const users = await User.find().sort({ createdAt: -1 });
  res.json(users);
});
```

This is used in the Admin Users page and Teams page.

Signup creates a new user.

Code block:

```js
router.post('/signup', async (req, res) => {
  const existing = await User.findOne({ email: req.body.email });
  if (existing) {
    return res.status(400).json({ message: 'Email already in use' });
  }

  const count = await User.countDocuments();
  const role = count === 0 ? 'Admin' : 'User';

  const user = new User({ ...req.body, role });
  const newUser = await user.save();
  res.status(201).json(newUser);
});
```

This checks for duplicate email, assigns a role, saves the user, and returns the new user.

Login verifies email and password.

Code block:

```js
router.post('/login', async (req, res) => {
  const user = await User.findOne({ email: req.body.email });
  if (!user) return res.status(404).json({ message: 'User not found' });

  if (user.password !== req.body.password) {
    return res.status(401).json({ message: 'Invalid credentials' });
  }

  res.json(user);
});
```

Role update is done with PUT /api/users/:id.

Code block:

```js
router.put('/:id', async (req, res) => {
  const updatedUser = await User.findByIdAndUpdate(
    req.params.id,
    { role: req.body.role },
    { new: true }
  );
  res.json(updatedUser);
});
```

Delete removes a user.

Code block:

```js
router.delete('/:id', async (req, res) => {
  await User.findByIdAndDelete(req.params.id);
  res.json({ message: 'User deleted' });
});
```


7. Contract Routes: routes/contractRoutes.js

Next is backend/routes/contractRoutes.js.

This file handles all contract APIs.

Code block:

```js
  destination: (req, file, cb) => cb(null, 'uploads/'),
  filename: (req, file, cb) => cb(null, `${Date.now()}-${file.originalname}`)
});

const upload = multer({ storage });
```

GET /api/contracts fetches contracts.

Code block:

```js
router.get('/', async (req, res) => {
  const { userId, userRole } = req.query;
  let query = {};

  if (userRole === 'User' && userId) {
    query = { createdBy: userId };
  }

  const contracts = await Contract.find(query).sort({ createdAt: -1 });
  res.json(contracts);
});
```

This route supports role-based data. Admin and Manager can see all contracts, while User can see only their own contracts.

GET /api/contracts/:id fetches one contract.

Code block:

```js
router.get('/:id', async (req, res) => {
  const contract = await Contract.findById(req.params.id);
  if (!contract) return res.status(404).json({ message: 'Contract not found' });
  res.json(contract);
});
```

POST /api/contracts creates a new contract.

Code block:

```js
router.post('/', async (req, res) => {
  const contract = new Contract(req.body);
  const newContract = await contract.save();
  res.status(201).json(newContract);
});
```

PUT /api/contracts/:id updates an existing contract.

Code block:

```js
router.put('/:id', async (req, res) => {
  const updatedContract = await Contract.findByIdAndUpdate(
    req.params.id,
    req.body,
    { new: true, runValidators: true }
  );
  res.json(updatedContract);
});
```

This update route is reused for approval, rejection, comments, risk resolution, editing, and document version updates.

POST /api/contracts/upload uploads a document.

Code block:

```js
router.post('/upload', upload.single('file'), (req, res) => {
  const fileUrl = `http://localhost:5000/uploads/${req.file.filename}`;
  res.json({
    url: fileUrl,
```

handleApprove moves a contract to the next stage.

Code block:

```jsx
const handleApprove = async () => {
  const nextStageIndex = (contract.stageIndex || 0) + 1;
  const stages = [...(contract.stages || [])];

  if (stages[contract.stageIndex]) {
    stages[contract.stageIndex].done = true;
    stages[contract.stageIndex].current = false;
  }

  if (stages[nextStageIndex]) {
    stages[nextStageIndex].current = true;
  }

  await fetch(`http://localhost:5000/api/contracts/${contractId}`, {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      stage: stages[nextStageIndex]?.name || 'Executed',
      stageIndex: nextStageIndex,
      stages
    })
  });
};
```

handlePostComment adds a comment to the timeline.

Code block:

19. Final Data Flow

Now I will summarize the full data flow.

The user opens the React frontend.

main.jsx renders App.jsx.

App.jsx controls navigation and logged-in user state.

LoginPage sends login requests to the Express backend.

The backend checks MongoDB using the User model.

After login, DashboardPage and ContractsPage fetch contracts from /api/contracts.

ContractDetailPage fetches one contract from /api/contracts/:id.

When a user creates, approves, edits, or comments on a contract, React sends POST or PUT requests to the backend.

The backend updates MongoDB using Mongoose models.

MongoDB stores users in the users collection and contracts in the contracts collection.

The updated data is returned to React, and React updates the UI.


Conclusion

To conclude, Nexus CLM is a full-stack application with a React frontend, Express backend, and MongoDB database.

The backend handles APIs, authentication logic, models, file upload, and seed data.

The frontend handles navigation, role-based access, dashboards, contract pages, user management, forms, and styling.
